# AGENTS.md

The inbox: one durable, addressable inbox per agent or person, for messages between agents in
different sessions and on different hosts. One service, `inbox serve`, with interchangeable
backends, specified in ESS before any code. The design is `docs/design/inbox.md`; read it before
changing anything.

Status: stage 1 of 6 is done; the 5 waves of stage 2 (`docs/plan/stage-2.md`) are
delivered, and waves 6 to 8, added after them: wave 6 delivered 2 of its 3 stories, wave 7
delivered story:dedup-key-scope and story:post-does-not-tell-a-message-id-exists on ESS 0.97.1,
and wave 8 delivered 6 stories filed from findings of the adversary passes.
Release 0.1.0 is the state of `main` after wave 3, release 0.2.0 the state after wave 8.
Release 0.3.0 is the state of `main` on 2026-11-22 after the changes its `CHANGELOG.md` section
lists: the landing figure and the 3 reference pages of the site, the test step that enforces
its budget, a specification without an `UNMAPPED` marker, no Python, and ESS 0.97.4.
Release 0.3.1 is release 0.3.0 with the changes under "Security" in its `CHANGELOG.md` section:
the deadline of a message, the record `collect` answers with, the control characters the
client prints, and the read rule and the unknown-message answer in the core.
The gate (see Rules) is open for principals of one operator. Stages 2 to 6 are the epics in
`.engineering/planning/epic/`.

| `crates/inbox-server/` | The HTTP service library: a loopback listener in front of the generated `server` feature, one thread per connection.   `task check` is green on the commit and 3 checks are green on it:
  `common / Security and privacy`, `inbox / task check` and `Build documentation`.

  requires the 3 checks on `main`, and a branch that is behind `main` is not refused for that.
  4 more let only the organization bot create, update or delete a branch or a tag, and require
  the bot as author and committer. Writing a ruleset or branch protection is the owner's act:
  `b10x-gates api` refuses it, and that refusal is not worked around.

  so every commit takes this route: push it to a branch as the bot

  `b10x-gates bot -- delete-branch <branch>`. First run: pull request 1, 2026-11-22. Never
  merge a pull request with GitHub's merge button: `main` holds only commits the bot wrote and
  committed.

## Rules

- Change `ess/` first. Never edit `generated/` by hand; `task check` fails on drift.
- `generated/rust/inbox` is never formatted, linted or edited: the synthesized code fails
  `cargo fmt --check` on ESS 0.97.4 (`cargo clippy -- -D warnings` failed on ESS 0.96.0 and was
  not measured again), and it stays outside the workspace, so neither step reads it. A crate
  depends on it by path (`inbox = { path = "../../generated/rust/inbox", features = ["server"] }`), implements the
  obligations named in its `PLAN.md` outside it, and adds itself under `crates/` without editing
  `Cargo.toml`. Never run `cargo fmt --all`: it formats path dependencies, this crate included, and
  `task drift` then fails on 16 files (2026-11-22). The gate runs `cargo fmt --check`.
- `ess/` holds no `UNMAPPED:` marker (the operator, 2026-11-22: "There must be no unmapped").
  A rule ESS cannot express is an `external:` outcome that states its reason, and
  `docs/design/inbox.md` lists it under "What the specification cannot say". `task spec` fails
  with the file and line of a marker.
- A scenario changes in its file under `ess/scenarios/` (`<name>.yaml`, with `scenario: <name>`);
  a scenario added or taken out is a file added or deleted, then `task scenarios` rewrites
  `ess/ess-inputs.yaml`; commit both.
- A generated scenario that synthesis refuses is claimed by an authored scenario's `covers:`
  list (in its file under `ess/scenarios/`), one claimant per id.
- No file of this repository is Python, and no task, workflow or document calls a Python
  interpreter (the operator, 2026-11-22: "No Python for permanent stuff."). A tool of the
  repository is a command of `crates/inbox-xtask`; a CI step that runs before the toolchain is
  installed is POSIX shell (`tools/gate-paths.sh`, run with `sh`).
