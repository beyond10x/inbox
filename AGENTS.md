# AGENTS.md

The inbox: one durable, addressable inbox per agent or person, for messages between agents in
different sessions and on different hosts. One service, `inbox serve`, with interchangeable
backends, specified in ESS before any code. The design is `docs/design/inbox.md`; read it before
changing anything.

Status: stage 1 of 6 is done; the 5 waves of stage 2 (`docs/plan/stage-2.md`) are
delivered, and waves 6 to 8, added after them: wave 6 delivered 2 of its 3 stories, wave 7
delivered story:dedup-key-scope and story:post-does-not-tell-a-message-id-exists on ESS 0.97.1,
and wave 8 delivered 6 stories filed from findings of the adversary passes.
Release 0.1.0 is the state of `main` after wave 3, release 0.2.0 the state after wave 8.
Release 0.3.0 is the state of `main` on 2026-11-22 after the changes its `CHANGELOG.md` section
lists: the landing figure and the 3 reference pages of the site, the test step that enforces
its budget, a specification without an `UNMAPPED` marker, no Python, and ESS 0.97.4.
Release 0.3.1 is release 0.3.0 with the changes under "Security" in its `CHANGELOG.md` section:
the deadline of a message, the record `collect` answers with, the control characters the
client prints, and the read rule and the unknown-message answer in the core.
Release 0.4.0 is release 0.3.1 with the changes its `CHANGELOG.md` section lists: TLS on the
loopback address with a pinned certificate, the client that opens its inbox again and reposts
by itself after a restart of the service, and a message past its deadline that takes no read
mark and ends no wait.
Release 0.5.0 is release 0.4.0 with the changes its `CHANGELOG.md` section lists: `inbox wake`,
the parameter `undelivered=1` of the wait on `Pending`, the Claude Code plugin in
`adapters/claude-code/`, and a text output that keeps each message to one line that is not
indented.
Release 0.6.0 is release 0.5.0 with the changes its `CHANGELOG.md` section lists: `inbox wake
--follow`, which shows each message in a terminal as it arrives, and a text output that shows
the characters that change the direction of text as their escapes.
Release 0.6.1 is release 0.6.0 with the changes its `CHANGELOG.md` section lists: an `inbox wake`
that ends with 4 and marks nothing when its reader is gone, a change of a file beside the outbox
that loses no line and follows no link, a text output that shows the characters of no width as
their escapes, and ESS 0.98.0.
The gate (see Rules) is open for principals of one operator. Stages 2 to 6 are the epics in
`.engineering/planning/epic/`.

## Publishing

- The repository is public at `https://github.com/beyond10x/inbox`. What must never enter it is
  in "Rules" below; the gates scan every push and refuse without printing the match.
- `main` moves only by the organization bot's fast-forward push through `b10x-gates`, after
  `task check` is green on the commit and 3 checks are green on it:
  `common / Security and privacy`, `inbox / task check` and `Build documentation`.
- The repository has 5 rulesets (read on 2026-11-22). "Required shared and repository gates"
  requires the 3 checks on `main`, and a branch that is behind `main` is not refused for that.
  4 more let only the organization bot create, update or delete a branch or a tag, and require
  the bot as author and committer. Writing a ruleset or branch protection is the owner's act:
  `b10x-gates api` refuses it, and that refusal is not worked around.
- A commit on which the 3 checks have not run is refused on `main` (`GH013`, "3 of 3 required
  status checks are expected"). The checks run on a pull request and on a push to `main` only,
  so every commit takes this route: push it to a branch as the bot
  (`b10x-gates publish --remote-ref refs/heads/<branch>`), open a pull request as the bot
  (`b10x-gates gh -- pr create`), wait for the 3 checks on its head, then fast-forward `main`
  to that commit. GitHub then shows the pull request as merged; delete the branch with
  `b10x-gates bot -- delete-branch <branch>`. First run: pull request 1, 2026-11-22. Never
  merge a pull request with GitHub's merge button: `main` holds only commits the bot wrote and
  committed.
- The site is the repository's own, at `https://beyond10x.github.io/inbox/` (route `/inbox/`).
  `.github/workflows/pages.yml` builds it on every push and pull request and, on `main`, uploads
  the build with `.well-known/b10x-site.json`; `.github/workflows/b10x-docs-site.yml` publishes
  that build through the organization's project-site workflow (pinned by commit), only for a
  push by `b10x-bot[bot]` to `main`. It is not part of the organization's shared documentation:
  no `b10x.docs.yaml`. A second push of `main` before the "Documentation site" run of the first
  push has published makes that run fail at its step "Verify caller authority" and cancels the
  first push's `check` run: land one commit per site publication, or both as one push.
- Build it locally with the two `npm` commands under "Commands". The specification pages are
  not copied: the site reads `generated/docs/docs` in place, `task projections` writes it, and
  `task check` fails when it differs from `ess/`.

  GitHub Release by the bot. A release holds no binary: the release workflow builds and attaches nothing, and `inbox` is built from source.
- No deployment exists.

## Rules

- Change `ess/` first. Never edit `generated/` by hand; `task check` fails on drift.
- `generated/rust/inbox` is never formatted, linted or edited: the synthesized code fails
  `cargo fmt --check` on ESS 0.98.0 (`cargo clippy -- -D warnings` failed on ESS 0.96.0 and was
  not measured again), and it stays outside the workspace, so neither step reads it. A crate
  depends on it by path (`inbox = { path = "../../generated/rust/inbox", features = ["server"] }`), implements the
  obligations named in its `PLAN.md` outside it, and adds itself under `crates/` without editing
  `Cargo.toml`. Never run `cargo fmt --all`: it formats path dependencies, this crate included, and
  `task drift` then fails on 16 files (2026-11-22). The gate runs `cargo fmt --check`.

  A rule ESS cannot express is an `external:` outcome that states its reason, and

  with the file and line of a marker.

  repository is a command of `crates/inbox-xtask`; a CI step that runs before the toolchain is
  installed is POSIX shell (`tools/gate-paths.sh`, run with `sh`).
